# Ch1 Vibe Coding 工作流（Day 3-4）

> **本章 JD 关键词**：AI 辅助开发
>
> **学完你能做什么**：掌握「提需求 → AI 生成 → 读懂 → 修改 → 修 bug」的完整工作流；会给 AI 写有条理的指令；能独立读懂并修改 AI 生成的代码；遇到报错知道怎么读、怎么让 AI 帮你修。交付一个自己每周都在用的周报生成器。

## 1. 心智转变：AI 是副驾，你是驾驶员

「Vibe Coding」容易滑向一个陷阱：**让 AI 全权代写，自己只负责说"好"**。但目标岗位的 JD 写的是「能使用 AI 辅助开发」——辅助的是**你**。面试官会指着项目代码问「这一行为什么这样写」，入职第一天就要在别人的代码上改功能。

所以本课程的 Vibe Coding 铁律：

> **AI 生成的每一行代码，你都要能说清它在干嘛。说不清的，要么问懂，要么删掉重来。**

工作流是一个循环，而不是「许愿一次、拿到成品」：

```
   ┌──────────────────────────────────────────┐
   │                                          │
   ▼                                          │
提需求 ──► AI 生成 ──► 读懂 ──► 修改 ──► 运行验证 ──┬─► 满意 → 交付
                                                      │
                                                  报错/不满意
                                                      │
                                                      ▼
                                                  修 bug / 再提需求
```

注意「**读懂**」和「**修改**」是两个独立环节：读懂是能解释，修改是能动手改。本章就是把这五步各自练一遍。

## 2. 读懂代码：三问法 + AI 出题考核（Day 3 上午）

### 2.1 每次拿到 AI 代码，先问三个问题

| 问题 | 在问什么 |
| --- | --- |
| 这个文件**整体**在干什么？ | 一句话说清（如「把流水账文本发给 GLM，把结果存成 md 文件」） |
| 每个**函数/代码块**在干什么？ | 输入是什么、输出是什么、谁调用它 |
| 我**改哪里**会改变什么？ | 找到那个「拧一下就有效果」的旋钮（比如 prompt 文本、模型名） |

三问答不上来的部分，就是你要追问 AI 的部分：**「解释第 X 行到第 Y 行在做什么，为什么要这样写」**。

### 2.2 AI 出题考核：验证你真的读懂了

自欺很容易（「我大概看懂了」），所以用考核闭环。AI 生成代码后，把这段指令发给它：

```text
你刚为我生成了这段代码。现在请你扮演严格的代码面试官，
针对这段代码出 3 道阅读理解题，考察我是否真的读懂了：
第 1 题问「这段代码整体在做什么」；
第 2 题问某个具体行为（如某个参数、某行的作用）；
第 3 题问「如果我改动某个地方，会发生什么」。
一次只出一道，等我回答后你先批改，再出下一道。
最后告诉我：3 题里答对了几题，哪部分理解有偏差。
```

**及格线：3 题答对 2 题。** 答错的题让 AI 讲解后，重新出一道同类题再答。

::: tip 为什么这招有效
向 AI 提问是「输入」，被考核是「输出」——只有输出才能暴露真实的理解缺口。这个习惯保持到课程结束，你的「读代码」能力会以每周可见的速度增长。
:::

## 3. 指令四要素：让 AI 一次做对（Day 3 下午）

同一个需求，指令质量决定你是一轮拿到能用代码，还是来回拉扯十轮。

### 3.1 差指令 vs 好指令

**差指令**（AI 只能瞎猜）：

> 帮我写个周报工具

AI 不知道：什么语言？输入从哪来？调哪个模型？输出成什么样？

**好指令**（四要素齐全）：

> **【任务】** 写一个 Python 脚本 `weekly_report.py`，把我的流水账整理成结构化周报。
> **【上下文】** 流水账以字符串形式写在脚本顶部的 `RAW_TEXT` 变量里；用 openai SDK 调 GLM（base_url 和 Key 从 `.env` 读取，环境变量名 `GLM_API_KEY`/`GLM_BASE_URL`）；模型用 `glm-4-flash`。
> **【约束】** 单文件、不超过 80 行；prompt 里要求模型按「本周完成 / 进行中 / 下周计划 / 需要支持」四节输出 Markdown。
> **【验收】** 运行 `python weekly_report.py` 后，当前目录生成 `weekly_report.md`，内容四节齐全、每条动词开头，我可以直接提交给领导。

### 3.2 四要素速查

| 要素 | 回答的问题 | 缺了会怎样 |
| --- | --- | --- |
| 任务 | 做什么、产出是什么文件 | AI 自由发挥，返工 |
| 上下文 | 输入从哪来、用什么库、环境如何 | 生成的代码和你的环境对不上 |
| 约束 | 语言/框架/格式/长度边界 | 用了你没学的东西，看不懂 |
| 验收标准 | 怎么证明做好了 | 你自己都不知道算不算完成 |

::: info 与 Ch2 的关系
把「指令四要素」里的【任务】换成任意业务、【约束】加上输出 JSON 格式，就是 Ch2 的 Prompt Engineering。本章只需要在**给编程助手提需求**时用熟它。
:::

## 4. 实战：周报生成器（Day 4 上午）

目标：完整走一遍五步循环，产出一个**你每周一早上真的会用**的工具。

### Step 0：建项目（2 分钟，Ch0 技能复热）

```powershell
mkdir weekly-report && cd weekly-report
python -m venv .venv
.venv\Scripts\activate
pip install openai python-dotenv
# 复制 Ch0 的 .env 过来（或照 .env.example 重写）
```

### Step 1：提需求

把 3.1 的「好指令」**用你自己的话重写一遍**发给 Claude Code（重写是为了逼你想清楚每要素）。

### Step 2：生成 + 读懂考核

拿到代码后先跑通，然后执行 2.2 的「AI 出题考核」，**3 题答对 2 题才继续**。

### Step 3：多轮修改（真正开始 vibe）

真实需求从来一轮做不完，依次提这三个修改需求，体验「修改」环节：

1. **改输出**：「周报每节最多 5 条，多余的合并；语气正式但不僵硬」
2. **改健壮性**：「如果 API 调用失败，给出人类能看懂的提示，告诉我去查 .env」（想想 Ch0 的 401）
3. **加功能**：「在周报末尾追加一节『本周关键词』，让模型从流水账里提炼 3 个词」

每轮修改后**重跑验证**——这就是「验收标准」的用法。

### 参考实现

课程仓库 [code/ch1-vibe-workflow/](https://github.com/your-name/learn-vibe-coding/tree/main/code/ch1-vibe-workflow) 提供 `weekly_report.py` 参考实现。**先自己生成，卡壳超过 20 分钟再对照**——直接抄参考实现 = 跳过本章全部训练。

## 5. 调试基本功：报错不可怕（Day 4 下午）

报错不是失败，是 Python 在**精确地告诉你哪里出了问题**。本节目的：建立「从下往上读 traceback」的肌肉记忆。

### 5.1 traceback 解剖

```
Traceback (most recent call last):              ← 固定开头，不用管
  File "weekly_report.py", line 25, in <module> ┐
    main()                                      │ 调用路径：
  File "weekly_report.py", line 21, in main     │ 谁调用了谁
    report = generate_weekly_report(RAW_TEXT)   ┘ （先跳过）
  File "weekly_report.py", line 12, in generate_weekly_report   ← 出错的位置
    return response.choices[0].message.content                  ← 出错的那一行
NameError: name 'response' is not defined       ← ★ 错误类型 + 原因，最先读这里
```

**读法：从最后一行开始往上。** 最后一行告诉你「什么错」，中间带行号的告诉你「在哪」，再往上是「怎么走到这的」。零基础 90% 的报错，看最后一行 + 出错行就能定位。

### 5.2 贴报错给 AI 的正确姿势

AI 修 bug 的效果，取决于你给它多少信息。模板：

```text
我运行 weekly_report.py 报了下面的错（完整复制，包括最后的错误类型行）：
【粘贴完整 traceback】

我期望：运行后生成 weekly_report.md
实际：直接报错退出了
已经试过：检查过第 12 行附近，没看出问题

请先告诉我原因是什么，再告诉我具体改哪几行。
```

三条红线：**traceback 要完整**（截图不如文字）、**期望 vs 实际都说清**、**先要解释再要改法**（不然下次还不会）。

### 5.3 预置 bug 修复实战（必做）

课程提供 3 段带 bug 的代码，在 [code/ch1-vibe-workflow/bugs/](https://github.com/your-name/learn-vibe-coding/tree/main/code/ch1-vibe-workflow/bugs)。对每段执行：**运行 → 自己从下往上读报错 → 说出猜测 → 贴给 AI 验证 → 修复 → 再运行验证**。

| 文件 | 你会遇到的报错 | 训练点 |
| --- | --- | --- |
| `bug1_name_error.py` | `NameError` | 变量名拼写：traceback 最后一行直指答案 |
| `bug2_indent_error.py` | `IndentationError` | Python 用缩进表示层级，多一层少一层都不行 |
| `bug3_api_401.py` | API `401` 错误 | **不是代码错，是环境错**：Key 没读到/写错——回忆 Ch0 的 `.env` |

bug3 特别重要：它教会你「报错不一定是代码问题」。修法提示：从 `.env` 正确读取 Key（答案就藏在 Ch0 的 `hello_llm.py` 里）。

::: tip 给自己建一本「错题本」
每次修完一个报错，在笔记里记一行：`报错类型 → 原因 → 解法`。四周课程结束时，这本错题本就是你私人的排错手册，也是面试前复习「踩坑经验」的素材。
:::

## 6. 自测门槛

进入 Ch2 前确认你能：

- [ ] 说全五步工作流，并能解释「读懂」和「修改」为什么是两个环节
- [ ] 独立写出包含四要素的指令（不看模板）
- [ ] 周报生成器是自己（和 AI）写出来的，且**通过了 AI 出题考核（3 对 2）**
- [ ] 3 段预置 bug 全部修复，bug3 能说清「为什么 401 不是代码错误」
- [ ] 拿到一段 traceback，能 30 秒内说出错误类型和出错行
- [ ] 周报生成器已 push 到 GitHub

## 7. 最小路径 vs 完整路径

- **最小路径（必做）**：第 1-5 节全部 + 自测门槛
- **完整路径（选做）**：
  - 让 AI 帮你给周报生成器**补全注释和类型标注**，对比它加的和你理解的是否一致
  - 初体验 `CLAUDE.md`：在项目根目录写一个文件告诉 AI 你的项目约定（Python 3.10+、依赖清单、代码风格），下次对话自动生效
  - 把 Ch0 遇到的报错补进你的错题本

## 8. 排错指引

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| AI 生成的代码直接跑不起来 | 上下文没说清环境（模型名、.env、库版本） | 用四要素重发指令，明确环境细节 |
| AI 答非所问 | 指令缺任务或验收标准 | 对照 3.2 表补要素，重发而不是追问十轮 |
| 对话越聊越乱、AI 记错前文 | 上下文被历史污染 | `/clear` 清空重开，把关键信息重新贴一遍 |
| AI 修 bug 越修越多错 | 只贴了半截报错 | 按 5.2 模板贴完整 traceback |
| 周报输出格式不稳定 | prompt 约束不严 | 这是 Ch2 的主题，先在指令里写死四节结构 |
| 出题考核一直不及格 | 生成代码超出当前理解太多 | 让 AI「用只学过变量/函数/字典/列表/HTTP 的水平重写」 |
