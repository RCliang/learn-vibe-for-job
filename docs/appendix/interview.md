## A. Prompt 工程

**A1. system 和 user 消息的区别？** 🎯
要点：system 定义全局角色/规则/输出格式，优先级高于 user；规则写 system 而不是每次在 user 里重复；模型本身无记忆，多轮是程序重发全部历史。

**A2. 怎么让模型稳定输出程序可处理的 JSON？**
要点：三层递进——prompt 约束（脆弱，会被代码块包裹）→ JSON mode（`response_format` 保证合法 JSON）→ Pydantic 校验（保证字段与类型正确，合法 JSON ≠ 字段正确）；失败把报错喂回模型自纠重试。

**A3. temperature 什么时候调高调低？**
要点：结构化/改写/分类用 0-0.3（稳定）；通用问答 0.4-0.7；创意脑暴 0.8+。结合项目答：知识库问答和 judge 评估都用了 0.2 以下。

**A4. few-shot 是什么？什么时候比描述有效？**
要点：给输入输出示例对；格式和风格难以用语言描述清楚时最有效；例子也消耗 token，要精简、要覆盖边界情况。

**A5. token 是什么？成本怎么算？**
要点：模型计费与长度单位，中文约 1 字 1-2 token；成本 =（输入+输出 token）× 单价；上下文窗口是单次可见上限，历史越长越贵越慢；调试看响应的 `usage` 字段。

## B. RAG

**B1. 讲讲 RAG 的原理和完整流程。** 🎯（白板题）
要点：解决模型不知道私有/最新知识的问题，对比微调（成本/更新周期）；离线：文档→切分→向量化→入库；在线：问题向量化→相似度检索 top-k→拼接 prompt→生成（带引用/拒答）；画两段流程图。

**B2. 切分策略怎么定？chunk 和 overlap 各解决什么？**
要点：chunk 太大检索不准、太小语义碎，中文常用 300-500；overlap 防关键句被切断在边界；**我的参数是评估选的**（对比过 300/600）。

**B3. 你的 top-k 为什么是这个值？** 🎯（项目深挖）
要点：不答「网上都这么设」——10 条测试问答集 + LLM as judge 对比 k=3/5，得分持平时选更省 token 的 3；有数据。

**B4. 幻觉怎么处理？** 🎯
要点：分层——生成侧（system 三纪律：只用资料/标注引用/诚实拒答 + 低温度）；检索侧（top-k 与切分调优让资料真的召回）；评估侧（Faithfulness 指标量化）；无法根除只能压制与度量。

**B5. 幻觉率怎么量化？**
要点：人工标注成本高；LLM as judge（测试集打分）；Ragas Faithfulness（答案 claims 被检索资料支持的比例，0-1）。

**B6. Ragas 四指标各评什么？低分怎么归因？** 
要点：Faithfulness（忠于资料，低→收紧 prompt）；AnswerRelevancy（切题，低→指令模糊）；ContextPrecision（检索准不准，低→调 chunk/embedding）；ContextRecall（检索全不全，低→调大 k/改切分）；先定位维度再改参数。

**B7. 向量检索的原理？为什么语义相近的文本能被检索到？**
要点：embedding 把文本映射为语义空间向量，余弦相似度度量接近程度；「年假」和「带薪休假」向量夹角小；向量库只管存和查，语义质量取决于 embedding 模型。

**B8. 为什么选 Chroma？**
要点：pip 即用、本地内嵌、零运维，适合中小规模；知道边界——超大规模/分布式要 Milvus 等；显式传入自选 embedding 模型（不用默认英文模型）。

**B9. RAG 效果不好，你的排查顺序？**
要点：先评估定位维度（检索 or 生成）→ 检索问题查切分/top-k/embedding、看实际召回的块；生成问题查 prompt 约束与温度；拒答过多可能是检索没召回。

**B10. GraphRAG 了解吗？什么场景需要？**
要点：向量 RAG 弱在多跳/枢纽（跨文档按实体关联）与全局汇总问题；GraphRAG 用 LLM 抽实体关系建图、沿边推理；代价是图构建的 LLM 成本与更新重算；我的原则：评估证明向量 RAG 不够时才升级。

## C. Agent 与 Function Calling

**C1. 白板画 Agent Loop，讲清原理。** 🎯
要点：LLM + 工具 + 循环；请求带 tools → 模型返回 tool_calls（或直接回答）→ 本地执行 → 结果以 role:"tool" 回填 → 下一轮；无 tool_calls 即最终答案；最大步数保险丝；**模型决策与执行分离**。

**C2. Function Calling 的完整流程？**
要点：JSON Schema 定义工具（name/description/parameters）→ tool_choice auto → 解析 `tool_calls`（arguments 是 JSON 字符串要 loads）→ 本地执行 → assistant 消息（含 tool_calls）原样入历史 + tool 消息回填。

**C3. 模型会执行函数吗？**
要点：**不会**——它只输出调用请求（名字+参数），执行永远在你的代码里；这正是安全设计的根基（执行权在我）。

**C4. 多轮对话的记忆怎么管理？** 🎯
要点：messages 累积机制；滑动窗口（按轮截断，保证 tool_calls 与 tool 结果成对不孤儿）；token 预算粗估兜底；摘要压缩（滑出窗口的压成要点入 system，滚动合并）；session 隔离；生产持久化换 Redis。

**C5. 什么是 Prompt Injection？Agent 场景为什么更危险？** 🎯
要点：用户输入里藏指令覆盖 system（数据被当指令）；纯聊天只是答错，Agent 有工具→被诱导执行危险动作；OWASP LLM Top 10 头号风险。

**C6. 注入怎么防？** 🎯
要点：三板斧纵深防御——输入过滤（正则拦典型话术，在调模型之前零成本）、指令数据隔离（system 声明用户消息是数据）、工具权限最小化（危险操作根本不注册）；没有银弹；正则可被变形绕过所以要多层。

**C7. 如果用户诱导你的 Agent 调用删除工具怎么办？** 🎯（项目深挖）
要点：我的项目里不存在删除工具（最小权限）；即使被诱导也只能调用只读工具；再加输入过滤与数据隔离两道前置防线；演示过三组攻击实验。

**C8. MCP 是什么，解决什么问题？**
要点：M 个应用 × N 个工具的适配爆炸 → 统一 client-server 协议，工具方写一次 Server 全平台可用；Claude Code 就是 MCP client。

**C9. 为什么手写 Loop 而不用 LangChain？**
要点：简单场景手写更透明好调试、理解原理；框架价值在多 Agent 编排与复杂状态时才出现；先懂本质再上框架，能判断「何时需要」比「会用」更重要。

## D. 工程与部署

**D1. 讲讲你的部署架构和流程。** 🎯
要点：ECS + Docker；本地/服务器构建镜像（Dockerfile 层缓存排序）；compose 管理（ports/env_file/restart: always）；密钥运行时 env_file 注入、不进 git 不进镜像；安全组只开必需端口；迭代三命令（pull → compose up -d --build）。

**D2. 为什么用 Docker 部署？**
要点：环境一致性（本地与服务器同镜像）；Dockerfile 可版本管理；compose 一键起停与自愈；层缓存让迭代构建秒级。

**D3. Dockerfile 里为什么依赖清单先 COPY？**
要点：层缓存规则——指令变了该层及之后全部重建；requirements 很少变放前面，改代码时 pip 层命中缓存秒级构建。

**D4. 镜像和容器的区别？**
要点：镜像=只读分层模板；容器=镜像+顶层读写层；同镜像可跑多容器；容器删了读写层数据丢失→持久化用 volume。

**D5. 密钥（API Key）你是怎么管理的？** 🎯
要点：本地 .env（gitignore）、云端 secrets/环境变量、容器 env_file 运行时注入；.dockerignore 排除；权限 600；泄露即轮换。

**D6. HTTPS 为什么需要？原理说个大概。**
要点：HTTP 明文可被中间人看；HTTPS=HTTP+TLS 加密；证书由 CA 背书证明公钥归属；个人项目 Let's Encrypt 免费 + certbot 自动续期。

**D7. 线上服务出问题，你怎么排查？**
要点：三板斧——`docker compose logs -f` 看日志 → grep ERROR 定位 → ps/health 确认存活；Ch1 的读 traceback 法对容器日志同样适用；磁盘/内存看 df。

**D8. 流式输出怎么实现的？**
要点：API `stream=True` 返回增量迭代器；界面边收边渲染（Streamlit write_stream）；前后端分离下用 SSE（text/event-stream，POST 流用 fetch reader 解析）。

## E. 项目深挖

**E1. 你项目里最难点是什么？**
要点框架：选一个真实的（如 tool 消息孤儿导致 API 报错 / 注入正则被变形绕过 / flush 缓冲导致日志不实时）→ 定位过程（读报错/实验）→ 解决 → 学到什么。**有细节才可信**。

**E2. 两个用户同时用你的服务会怎样？**
要点：内存 dict 按 session 隔离目前可用；诚实说边界——并发大会锁/内存问题，生产上 Redis 或数据库存会话；能说出局限就是加分。

**E3. 你的项目如果用户量上来，哪里先扛不住？**
要点：每请求同步等 LLM 响应（并发受限，异步/队列）；内存记忆与单实例（水平扩展要外部化状态）；这题考的是「知道自己系统的边界」。

**E4. 为什么选 GLM 不用 OpenAI？**
要点：国内可用零翻墙、OpenAI 兼容接口（openai SDK + base_url）、切换成本低；工程上「模型可替换」本身是设计点。

**E5. 评估为什么重要？你的评估怎么做？**
要点：没有评估的调优是玄学；10 条测试问答集 + LLM as judge（1-5 分 JSON 输出）+ 多组参数对比记录 jsonl；引申 Ragas 四指标。

**E6. 项目还能怎么改进？（送分题，提前备好）**
要点：SSE 流式、会话持久化、file_uploader 动态语料、混合检索/rerank、摘要压缩记忆、监控告警——课程完整路径里列过的都是。
