01

Prompt Engineering 与消息角色

Ch1 的四要素写给编程助手，这一章同样的四要素写给模型本身——Ch3 的检索模板、Ch4 的系统指令，还是 prompt。
Agent 也能帮你写提示词，但判断一份 prompt 好坏的能力得自己长——后面调试应用 trace 时，它很值钱。

01 · 从指令四要素到 Prompt Engineering

四要素搬家：从「给编程助手」到「给模型」

给编程助手（Ch1）给模型（Ch2）
任务system prompt 里的角色与任务定义
上下文user 消息里每次贴进去的材料
约束输出格式、语气、规则
验收标准few-shot 示例 ＋ Pydantic 校验

⬆ 验收从「人肉看」升级成「机器卡」

few-shot 示例让模型知道「长什么样算对」，Pydantic 校验让它「不对就过不了关」。这两件武器就是本章的主角，待会儿挨个登场。

四要素一个没变

只是换了收信人。把【任务】换成任意业务、【约束】里加上「输出 JSON」，这就是你以后天天要用的模板。

01 · messages 的三种角色

三个角色，各司其职

messages = [ {"role": "system", "content": "你是资深简历顾问， 只给具体可执行的建议"}, # 全局设定 {"role": "user", "content": "我的简历是：……"}, # 本次输入 {"role": "assistant", "content": "好的，我先看 工作经历部分……"}, # 历史回复 ]
角色作用类比
system定义「它是谁、守什么规矩」员工手册
user每次的具体输入工单
assistant模型之前的回复聊天记录

① 模型本身没有记忆

你看到的「连续对话」，是程序把历史消息每次完整重发——所以对话越长，越慢、回复效果越差。这就是上下文需要压缩管理的底层原因。

② system 的优先级高于 user

角色、规则、输出格式一律写进 system，别每次在 user 里重复。而且 system 尽量不要变——会影响 KV cache，这个我们后面再聊。

01 · system prompt

好 system prompt 的四件套

公式
角色（你是谁）＋ 任务（做什么）＋ 规则/边界（必须怎样、绝不怎样）＋ 输出格式（以什么形式返回）

缺角色

回答像百科全书——正确，但没用，不知道替谁说话。

缺规则

输出空洞、没有明确指向——它不知道什么必须做、什么绝不能做。

缺输出格式

后面没法结构化对接——程序拿不到能解析的数据。

01 · few-shot

给例子，胜过给描述标准难用语言描述的时候，一对示例顶一堆形容词

❌ 描述式（模型不知道你的标准）

「把简历句子改得专业、有力、量化。」

你说的「专业」到底是什么标准？到什么程度？

模型没有办法理解你要求的“专业”是什么，只能按自己的默认审美发挥。

请按下面的风格改写简历句子。 输入：负责公司内部系统的开发维护工作 输出：独立负责 3 个内部系统的开发与迭代，将工单处理时长从 2 天压缩至 4 小时 现在改写：用 Python 写接口，也用过一些 AI 相关的接口

量化数字、动词开头、成果导向——这就是有控制的边界，LLM 就能理解“专业”指的就是这样的输出标准。

所以：例子一定要覆盖你想控制的边界，尽可能泛化。

02

温度、参数与 token 账本

prompt 决定下限，参数决定性格。
这一部分的实验精神就一句话：调参之前，先亲眼看现象。

02 · temperature

temperature：模型的性格旋钮

原理一句话：LLM 是一个词一个词往外蹦的，每蹦一个词之前，手里都有一份「候选词概率排行榜」——temperature 调的就是这份榜单的差距：调低，第一名的优势拉到无限大；调高，冷门词也有机会被选中。

temperature效果适用任务
0 – 0.3刻板、稳定、可复现结构化输出、分类、改写 ▸ 简历优化器
0.4 – 0.7平衡周报、总结、通用问答
0.8 – 1.0发散，有惊喜也有惊吓头脑风暴、创意文案

top_p：另一档随机性旋钮，管候选名单本身——不动概率差距，直接砍名单（top_p=0.1 = 只从累计概率 10% 的头部挑）。和 temperature 殊途同归，实战改一个就够；max_tokens 是输出上限，当保险丝防烧钱。

🧊 泼冷水：它没那么重要

推理类模型（如 deepseek-reasoner），API 层面不让调 temperature，设了也被忽略；输出稳定靠的是后面的 JSON mode + 校验。真正的重点是它背后的概念：LLM 的输出是从概率分布里采样出来的——这个认知比记参数值钱。

🎬 弹幕猜一下：团队脑暴取名用哪档？ → 往 1.0 靠，就怕它太规矩
02 · token 账本

token：模型眼里的文字

1

token 是模型读写的最小单位

你看到的文字，模型看到的是一串 token。直觉：1 个汉字 ≈ 1~2 token，1 个英文单词 ≈ 1 token——越生僻切得越碎

2

各种「窗口」「上限」，单位都是 token

「上下文 128K」≈ 一次装下十三万 token；max_tokens 限的是输出的 token 数

3

计费也按 token

成本 =（输入 ＋ 输出）× 单价。DeepSeek 是主流里最便宜的一档，本章全部练习 < 1 元；每次调用后看一眼 response.usage

🍓 懂了它，很多现象就通了

经典的「strawberry 里有几个 r」，模型老数错——

因为它看到的不是 s-t-r-a-w-b-e-r-r-y 一个个字母，而是切成几块的 token。字母层面它根本「看」不到。

对话越长 → 重发 token 越多 → 越贵、越慢、效果越差——「对话太乱就 /clear」的底层原因。

03

结构化输出

JSON 是数据的世界语——但模型吐出来的是文本，你的程序要的是数据。把文本变成数据，是工程化最重要的基石。
顺带认识 Function Calling：把函数登记给模型，它用 JSON 报函数名和参数（Ch4 详讲）——这章先练「让模型可靠输出数据」。
跟着仓库里的 json_parsing_demo.py，step1 → step3 一步步跑。

03 · 三步演进 · 第 1→2 步

从「口头约定」到 JSON mode第 1 步的翻车不用单独记——它就是第 2 步存在的理由

第 1 步 · 只靠 prompt 约束（脆弱）

prompt 写「只输出 JSON」→ 模型套 ```json 代码块、加「好的，以下是您要的」→ json.loads 当场崩。不是「错」，是不可靠：跑 5 次崩 1 次，演示好好的，上线才炸。

response = client.chat.completions.create( model=MODEL, messages=[ {"role": "system", "content": "你是信息抽取助手。按此结构返回：" '{"name": "…", "city": "…", "skills": ["…"]}'}, {"role": "user", "content": "张小明，杭州，会 Python、Docker"}, ], response_format={"type": "json_object"}, # ← 开启 JSON mode ) data = json.loads(response.choices[0].message.content) # 纯 JSON，直接解析

第 2 步 · 两个要点

① 目标结构的骨架写在 system 消息里，别写 user 里
② 开启后 content 就是纯 JSON——不用再剥壳

不只是 DeepSeek

OpenAI / Qwen / Kimi / GLM / Mistral：response_format={"type":"json_object"}，写法几乎通用
Gemini：responseMimeType: "application/json"
Claude：2025 年底也补上了正式的 Structured Outputs
行业通用能力，学一次到处用

03 · 三步演进 · 第 3 步

Pydantic 校验（工程级）合法 JSON ≠ 字段正确——用类型定义一劳永逸

from pydantic import BaseModel class ContactInfo(BaseModel): name: str city: str skills: list[str] # 返回成字符串？在这精确报错 info = ContactInfo.model_validate(data) # 字段名/类型不对 → ValidationError 指到具体字段 print(info.skills[0]) # 之后有代码补全，像普通对象一样用

JSON mode 的盲区

它只保证「是合法 JSON」，不保证字段和类型符合约定——你说 skills 要数组，它可能返回一整个字符串。记住：合法 JSON ≠ 字段正确。

自测练习

把 skills: list[str] 改成 skills: str，跑一次看 ValidationError 报什么，再改回来。

后端必用库

Python 后端开发必用，也是 FastAPI 的内置校验库，Ch4 项目二还会重逢——几乎是必须掌握的。pip install pydantic

03 · 三步演进 · 失败了怎么办

把报错喂回去：自纠重试

校验失败ValidationError→ 报错原样发回作为新消息喂给模型→ 它自己改重试一次
你返回的 JSON 中 skills 应为数组，实际返回了字符串。 请修正后重新输出完整 JSON。

—— 把 ValidationError 的关键信息翻译成这句话，作为新消息发回去

🚫 千万别自己上手修字符串

截断、去代码块、补引号……那是无底洞——模型有一百种方式出错。

生产环境的通用模式

自纠重试（retry with feedback）——简历优化器里你会亲手实现它。

04

实战：简历优化器

第四部分，实战一个简单的作业。需求一句话：输入一段简历文本 → 输出结构化的改进建议。
为什么选它？够真实——使用频率比较高、手边必然有资料的一个场景。

04 · 实战 · 设计先行

结构先行：先设计输出，再写 prompt

字段含义
overall_score总分 0–100
strengths保留的优点，最多 3 条
issues问题清单：维度（内容/表达/关键词/结构）＋ 问题 ＋ 建议
star_rewritesSTAR 改写示例：原句 → 改写 → 理由
keywords_to_add建议补充的关键词

为什么先设计结构

先想清楚要什么，再写 prompt——prompt 才有的放矢。

这份设计就是下一页 v2 里的输出模型（整个程序的「合同」），也是你交给 AI 的验收标准。

04 · 实战 · 最终形态

v2 标准写法：代码让 AI 写，规格你来定v0 的脆弱、v1 的 JSON mode 第 12 页都跑过了——直接看最终形态长什么样

# ① 输出模型：上一页五个字段落成「合同」 class ResumeReview(BaseModel): overall_score: int strengths: list[str] issues: list[Issue] # 维度＋问题＋建议 star_rewrites: list[StarRewrite] # 原句→改写→理由 keywords_to_add: list[str] # ② JSON mode ＋ 校验 ＋ 自纠重试 def optimize(resume: str) -> ResumeReview: data = call_llm(build_messages(resume)) # JSON mode try: return ResumeReview.model_validate(data) except ValidationError as exc: fixed = call_llm(feedback(exc)) # 报错喂回 return ResumeReview.model_validate(fixed) # ③ JSON 是手段，报告才是产物 print_report(optimize(SAMPLE_RESUME))
============================================== 简历总分：58 / 100 ============================================== [保留的优点] + 有完整的 RAG 项目经历，切中技术方向 [问题清单] 1. [内容] 负责公司内部系统的开发维护工作 -> 建议：拆出系统数量与量化结果 2. [表达] 工作认真负责，经常主动加班 -> 建议：删主观评价词，「加班」是减分项 [STAR 改写示例] 原句：负责整个项目的开发，用了大模型和向量数据库…… 改写：独立完成企业知识库问答系统——GLM + Chroma， 评估 4.6/5，Docker 部署上线 理由：原句职责堆砌无结果；改写补齐行动与量化结果 [建议补充的关键词] RAG、Function Calling、FastAPI、Docker

验收口径：「能跑」不算完成，长这样才算——五板块齐全、每条带维度建议、过 Pydantic 校验；先 sample_resume.txt，再你自己的。

VIBE CODING 时代还要自己写吗 不用——这套程序就该让 AI 写。但五个字段的结构设计，就是你的需求书和验收标准：过没过校验、bug 出在哪，你得看得懂；「要什么」「长什么样算好」，得你告诉 AI。
