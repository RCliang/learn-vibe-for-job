Ch3 RAG 的「检索结果拼接模板」是 prompt，Ch4 Agent 的「系统指令与工具描述」还是 prompt。这页不是本章限定知识，是天天要用的模板。

01 · messages 的三种角色

三个角色，各司其职

messages = [ {"role": "system", "content": "你是资深简历顾问， 只给具体可执行的建议"}, # 全局设定 {"role": "user", "content": "我的简历是：……"}, # 本次输入 {"role": "assistant", "content": "好的，我先看 工作经历部分……"}, # 历史回复 ]
💡 多轮对话的真相

模型本身没有记忆。你看到的「连续对话」，是程序每次把历史消息完整重发。Ch4 讲记忆管理时它会变成必须亲手处理的问题。

角色作用类比
system定义「它是谁、守什么规矩」员工手册
user每次的具体输入工单
assistant模型之前的回复聊天记录

记法

Ch0 你已经写过 messages 列表——现在你知道那两个键值对各是什么身份了。

01 · system prompt

两个要点，一个公式

① 多轮对话 = 往列表里追加消息

「程序每次完整重发历史」的实现，就这么朴素——列表越来越长，token 越烧越多（第 10 页细算账）。

② system 的优先级高于 user

角色、规则、输出格式都写进 system，别在 user 里重复：一费 token，二聊久了模型会漂。

公式 · 四件套
角色（你是谁）＋ 任务（做什么）
＋ 规则/边界（必须怎样、绝不怎样）＋ 输出格式（以什么形式返回）
01 · few-shot

给例子，胜过给描述格式难描述、风格难定义的时候，一对示例顶一堆形容词

❌ 描述式（模型不知道往哪使劲）

「把简历句子改写得更好，要专业、有力、量化。」

每个词都对，但——
· 「专业」长什么样？
· 「有力」到什么程度？
· 「量化」必须每句都有数字？

模型只能按自己的默认审美发挥。

请按下面的风格改写简历句子。 输入：负责公司内部系统的开发维护工作 输出：独立负责 3 个内部系统的开发与迭代，将工单处理时长从 2 天压缩至 4 小时 现在改写：用 Python 写接口，也用过一些 AI 相关的接口

想要什么，例子自己会说话：量化数字、动词开头、成果导向——全在示例里。
两个提醒：例子要覆盖你想控制的边界；例子本身也在烧 token，够用就好。

02

温度、参数与 token 账本

两个话题一个性质：都是旋钮。
拧之前先知道拧它改变什么，以及每一圈多少钱。

02 · temperature

temperature：模型的性格旋钮

temperature效果适用任务
0 – 0.3刻板、稳定、可复现结构化输出、分类、改写
▸ 本章简历优化器
0.4 – 0.7平衡周报、总结、通用问答
0.8 – 1.0发散，有惊喜也有惊吓头脑风暴、创意文案

另外两个参数，知道存在即可

max_tokens 输出长度上限——当保险丝用，防失控烧钱
top_p 和 temperature 类似的另一档旋钮——一般不动

🧪 实验：亲眼看温度的差异

code/ch2-prompt/temperature_lab.py

同一个 prompt「用一个比喻解释什么是 temperature 参数」，在 0.2 / 0.7 / 1.0 下各跑一次，对比输出差异。

调参之前先看现象——这是本章的实验精神。

02 · token 账本

每次调用多少钱从今天起建立成本意识——它决定你敢不敢把 API 用进真实项目

1

token 是计费和计长度的单位

直觉：1 个汉字 ≈ 1~2 token，1 个英文单词 ≈ 1 token

2

上下文窗口 = 一次能「看到」的 token 上限

聊天记录越长，每次重发的 token 越多——越贵也越慢。这就是 Ch1 说「对话太乱就 /clear」的底层原因

3

成本 =（输入 token ＋ 输出 token）× 单价

DeepSeek 是主流模型里最便宜的一档，本章全部练习 < 1 元

response = client.chat.completions.create(...) # 每次调用后看一眼： print(response.usage) # prompt_tokens 输入 # completion_tokens 输出 # total_tokens 总量

养成习惯

usage 字段告诉你这次花了多少 token——跑几次简历优化器，你就能估出单价量级。

03

结构化输出

模型天生吐的是文本，程序要的是数据。
三步演进：从脆弱到可靠——「聊天玩具」到「应用」的分水岭。

03 · 三步演进 · 第 1 步

只靠 prompt 约束（脆弱）prompt 里写「只输出 JSON」，然后 json.loads 一把梭

content 拿到手，长这样： 好的，以下是您需要的 JSON： ```json {"name": "张小明", "city": "杭州", "skills": ["Python", "Docker"]} ``` 已为您整理完毕，如需调整请随时告诉我。 data = json.loads(content) json.JSONDecodeError: Expecting value: line 1 column 1

它不是「错」，只是不可靠

· 套 ```json 代码块
· 前后加「好的/完毕」说明文字
· 单引号、尾逗号、中途换风格……

跑 5 次，总有一次不合规。工程要的是「每次都行」，不是「大概率行」。

03 · 三步演进 · 第 2 步

JSON mode（可靠）一个参数，白纸黑字告诉模型：这次必须输出合法 JSON

response = client.chat.completions.create( model=MODEL, messages=[ {"role": "system", "content": "你是信息抽取助手。按此结构返回：" '{"name": "…", "city": "…", "skills": ["…"]}'}, {"role": "user", "content": "张小明，杭州，会 Python、Docker"}, ], response_format={"type": "json_object"}, # ← 开启 JSON mode ) data = json.loads(response.choices[0].message.content) # 纯 JSON，直接解析

两个要点

① 目标结构的骨架写在 system 消息里
② 开启后 content 是可直接解析的纯 JSON——不用再剥壳

但它只管「合法」

把 skills 该有的数组写成一个字符串？JSON mode 照样放行——崩在下游。字段级把关，看第 3 步。

03 · 三步演进 · 第 3 步

Pydantic 校验（工程级）合法 JSON ≠ 字段正确——用类型定义一劳永逸

from pydantic import BaseModel class ContactInfo(BaseModel): name: str city: str skills: list[str] # 返回成字符串？在这精确报错 info = ContactInfo.model_validate(data) # 字段名/类型不对 → ValidationError 指到具体字段 print(info.skills[0]) # 之后有代码补全，像普通对象一样用
校验失败ValidationError→ 报错喂回模型作为新消息发回→ 重试一次自纠重试

失败了怎么办

不要人工修补——把报错原文发回模型让它自己改。生产环境处理模型输出的通用模式。

JD 常客

FastAPI 的内置校验库，Ch4 项目 2 再遇。pip install pydantic

04 · 实战 · 开发路径

三级跳：v0 → v1 → v2也是本章知识的完整复览

v0 · prompt 约束体验脆弱：跑 5 次，总有一次解析失败？→ v1 · JSON mode结构写进 system——稳定了→ v2 · Pydantic ＋ 自纠重试 ＋ 友好打印对照验收口径交付

迭代练习 ×2

① temperature 0.7 → 0.2，对比建议稳定性

完成后：AI 出题考核（Ch1 复用）

让 AI 针对你的 Pydantic 模型出 3 道题——比如「把 overall_score 返回成 "85 分" 字符串会发生什么？」3 对 2 通关。

这套「结构 → prompt → 校验 → 自纠」的组合拳，就是 Ch3 RAG、Ch4 Agent 里处理模型输出的标准姿势。
