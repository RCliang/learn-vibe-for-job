## 第 1 页 · 封面（开场 Hook）

上一章你和 AI 结对写出了周报生成器，练的是给**编程助手**提需求。这一章镜头掉转，对准**模型本身**——怎么跟大模型说话，让它稳定交出你要的东西。这门手艺有个正式名字：Prompt Engineering。去搜一圈 Agent 岗的 JD，出现频率第一的技能词就是它。

我是AI摸鱼的梁师傅，今天讲 Ch2 Prompt 工程实战。交付物也很实在：一个你求职当天就用得上的**简历优化器**——AI 给你的简历打分、挑毛病、按 STAR 法则改写，而且每一条建议都是程序能直接消费的结构化数据。

## 第 2 页 · 本章路线

先看地图，这一章横跨三天。Day 5 讲怎么给模型写指令：messages 三种角色、few-shot 给例子、温度参数，顺手建立 token 成本意识——从这天起，每次调用花多少钱你心里都得有数。Day 6 只干一件事：结构化输出，让模型吐出来的东西程序能直接用——这是从「聊天玩具」到「应用」的分水岭。Day 7 周末实战，把前两天的东西全部捏进简历优化器。

丑话说前头：这一章是全课程的地基。Ch3 RAG 的检索拼接模板是 prompt，Ch4 Agent 的系统指令还是 prompt。**prompt 写不好，上层架构再漂亮也没用。**

## 第 3 页 · 01 · 分隔页：写给模型的指令

第一部分，写给模型的指令。你已经会写四要素了，这部分做一次搬家——把给编程助手的那套家什，平移到给模型本身。家什不变，住处变了，验收方式还顺带升了个级。

## 第 4 页 · 四要素搬家：从「给助手」到「给模型」

搬家怎么搬，看这张映射表。任务，变成 system prompt 里的角色与任务定义；上下文，变成 user 消息里的输入材料；约束，变成输出格式、语气、规则。

重点是最后一条：验收标准。给编程助手，验收靠你自己看；给模型，验收可以上机器——**few-shot 示例**让它知道「长什么样算对」，**Pydantic 校验**让它「不对就过不了关」。验收从人肉升级成了自动，这也是本章最有含金量的一次升级。

## 第 5 页 · messages 的三种角色

正式认识 messages 列表。三个角色各司其职：`system` 定义它是谁、守什么规矩，类比**员工手册**；`user` 是每次的具体输入，类比**工单**；`assistant` 是模型之前的回复，类比**聊天记录**。

顺便戳破一个幻觉：**模型本身没有记忆**。你看到的「连续对话」，是程序每次把历史消息完整重发一遍。现在记住这个结论就行，Ch4 讲记忆管理时，它会变成必须亲手处理的问题。

## 第 6 页 · 两个要点 + 四件套公式

两个要点。第一，多轮对话就是往列表里追加消息——上面说的「重发机制」，实现层面就这么朴素。第二，**system 的优先级高于 user**。所以角色、规则、输出格式都应该写进 system，别每次在 user 里重复：一是费 token，二是聊久了模型会漂。

好 system prompt 有个公式，叫四件套：**角色**（你是谁）＋**任务**（做什么）＋**规则边界**（必须怎样、绝不怎样）＋**输出格式**（以什么形式返回）。周末那个简历优化器的 system prompt，就是照这个模子长出来的。

## 第 7 页 · few-shot：给例子胜过给描述

当你要求一种「格式难描述、风格难定义」的输出时，与其写一堆形容词，不如直接给一对例子。看屏幕：反例是「改写得专业、有力、量化」——每个词都对，但模型不知道往哪使劲。正例直接给一对输入输出：「负责内部系统开发维护」改写成「独立负责 3 个系统，工单处理时长从 2 天压到 4 小时」。你想要什么，**例子自己会说话**。

两个提醒：例子要覆盖你想控制的边界——量化数字、动词开头、成果导向，全在例子里；还有，**例子本身也在烧 token**，够用就好。

## 第 8 页 · 02 · 分隔页：温度、参数与 token 账本

第二部分，温度、参数与 token 账本。这两个话题一个性质：都是旋钮。拧之前先知道拧它改变什么，以及每一圈多少钱。

## 第 9 页 · temperature：模型的性格旋钮

temperature，模型的性格旋钮，三档。低档 0 到 0.3，刻板、稳定、可复现——结构化输出、分类、改写用它，本章简历优化器就锁低档。中档 0.4 到 0.7，平衡，周报、总结、通用问答。高档 0.8 到 1.0，发散，有惊喜也有惊吓，留给头脑风暴和创意文案。

另外两个参数知道存在就行：`max_tokens` 是输出长度上限，当保险丝用，防失控烧钱；`top_p` 是类似的另一档旋钮，一般不动。

仓库里有个 temperature_lab.py：同一个 prompt「用一个比喻解释 temperature」，在 0.2、0.7、1.0 下各跑一次。**建议真跑一遍，调参之前先看现象**——这是本章的实验精神。**跑完的把三次输出发评论区**，我看看谁的 1.0 最离谱。

## 第 10 页 · token 账本：每次调用多少钱

从今天起建立成本意识。token 是模型计费和计长度的单位，直觉：一个汉字约 1 到 2 个 token，一个英文单词约 1 个 token。上下文窗口是模型一次能看到的 token 上限——聊天记录越长，每次重发的越多，**越贵也越慢**。这就是 Ch1 说「对话太乱就 /clear」的底层原因。

成本公式很简单：**输入 token 加输出 token，乘单价**。DeepSeek 是主流模型里最便宜的一档，**本章全部练习加起来不到一块钱**。养成习惯：每次调用后看一眼响应里的 `usage` 字段，它告诉你这次花了多少 token。

## 第 11 页 · 03 · 分隔页：结构化输出

第三部分，结构化输出。Ch0 说过，JSON 是数据的世界语；但模型天生吐的是**文本**，你的程序要的是**数据**。这一部分就是干这个的——三步演进，从脆弱到可靠，也是从玩具到应用的分水岭。

## 第 12 页 · 第 1 步：只靠 prompt 约束（脆弱）

第一步，只靠 prompt 约束：在 prompt 里写「只输出 JSON」，然后 `json.loads` 一把梭。翻车现场长这样：模型给 JSON 套上 markdown 代码块，或者前后加两句「好的，以下是您要的」——解析当场崩。

注意我的措辞：它不是「错」了，它只是**不可靠**。跑五次，总有一次不合规。工程上我们要的是「每次都行」，不是「大概率行」。

## 第 13 页 · 第 2 步：JSON mode（可靠）

第二步，开 JSON mode。调用时加一个参数：`response_format` 的 type 设成 `json_object`，白纸黑字告诉模型——这次必须输出合法 JSON。

两个要点：结构描述要写进 **system** 消息，把目标 JSON 的骨架直接给它看；开启之后拿到的 content 就是纯 JSON，`json.loads` 直接解析，不用再剥壳。

## 第 14 页 · 第 3 步：Pydantic 校验（工程级）

但 JSON mode 只保证「是合法 JSON」，不保证**字段和类型**符合你的约定——模型把本该是数组的 skills 写成一个字符串，JSON mode 不管，崩在下游。第三步上 Pydantic：定义一个类，声明每个字段的类型；`model_validate` 一过，字段名不对、类型不对，**精确报错指到具体字段**。过了校验就是普通 Python 对象，有代码补全，用起来跟本地类没区别。

校验失败别人工修补——把报错原文作为新消息发回模型，让它自己重试一次。这叫**自纠重试**，生产环境的通用模式，简历优化器里会亲手实现。顺便说，Pydantic 是 JD 里的常客，FastAPI 的内置校验库，Ch4 还会再遇到它。

## 第 15 页 · 04 · 分隔页：周末实战 · 简历优化器

第四部分，周末实战：简历优化器。三天知识的总装车间——system 四件套、few-shot、低温、JSON mode、Pydantic、自纠重试，一个不落全用上。这工具从今天起就是你的求职装备。

## 第 16 页 · 结构先行：先设计输出模型

动手前先想清楚要什么。这是 Prompt Engineering 的进阶心法，叫**结构先行**：先设计 Pydantic 输出模型，再回头写 prompt。

五个字段：`overall_score` 总分 0 到 100；`strengths` 保留的优点，最多 3 条；`issues` 问题清单，每条带维度、问题、建议；`star_rewrites` 改写示例，原句、改写、理由三件套；`keywords_to_add` 建议补充的 JD 关键词。

STAR 提前剧透：**情境、任务、行动、量化结果**。Ch8 求职冲刺的主力方法论——你简历里每一句经历，都要经得起 STAR 检验。

## 第 17 页 · 验收口径：跑出来长这样才算

程序跑出来长什么样？屏幕上这份终端报告：总分 58；保留的优点；问题清单按内容、表达、关键词分维度，每条带建议；STAR 改写——原句是职责堆砌没结果，改写补齐行动和量化；最后是建议补充的关键词。中间的 JSON 只是技术手段，**对使用者可见的是这份报告**。

验收口径说死：「能跑」不算完成——跑 `sample_resume.txt`，五板块齐全、每条 issue 带维度和建议、通过 Pydantic 校验，**跑出来长这样才算**。那份 sample 是典型差简历：口语化、无量化、职责堆砌。先跑它，再跑你自己的。

## 第 18 页 · 开发路径：v0 → v1 → v2

开发路径三级跳。v0 只靠 prompt 约束，专门体验脆弱性——跑五次，总有一次解析失败？那就是它。v1 开 JSON mode，结构写进 system——稳了。v2 上 Pydantic 校验、自纠重试、友好打印，对照上一页的口径交付。

做完还有两个迭代练习：temperature 从 0.7 调到 0.2，对比建议稳定性；往 prompt 里加一对 few-shot 改写示例，看 star_rewrites 的质量变化。最后复用 Ch1 的**AI 出题考核**：让 AI 针对你的 Pydantic 模型出三道题，比如「模型把 overall_score 返回成『85 分』字符串会发生什么」，三对两通关。**跑通的弹幕刷个 🎉**。

## 第 19 页 · 排错速查表

排错速查表，六个高频现象，对着症状找解法。`JSONDecodeError`：多半没开 JSON mode，或 system 里没写清结构。Pydantic 的 `ValidationError`：把报错喂回模型重试，走自纠那套。输出说一半停了：`max_tokens` 太小。建议又空又水：prompt 只有角色没有规则——补四件套的第三件。`429` 限流：sleep 两秒再试。few-shot 加了反而更贵：例子砍到一行输入一行输出。

这张表建议截屏存着，Day 7 写作业时会反复用到。

## 第 20 页 · 通关自测 + 预告（结尾 CTA）

最后体检，六条。默写四件套公式，说得出为什么规则放 system 不放 user；给「简历改写」和「团队脑暴取名」各配一个 temperature 并说理由；能讲清 JSON mode 和 Pydantic **各自**解决什么问题——提示：合法 JSON 不等于字段正确；亲手把 `overall_score` 从 int 改成 str，跑一次看 ValidationError 长什么样，再改回来；简历优化器跑出五板块报告、过 Pydantic 校验，看一眼 usage 能估出这次调用花了多少 token；最后，push 上 GitHub。

六条全过，恭喜——JD 上那个出现频率第一的技能词，你已经能**拿着实物**对面试官讲了。
