## 第 1 页 · 封面（开场 Hook）

上一章你的周报生成器已经跑起来了。接下来我们就要学会怎么让模型按固定格式输出，LLM的输出随机性注定了需要一些手段来固定输出，尤其是你的程序需要的是结构化的语言，而不是自然语言。

大家好，我是AI摸鱼的梁师傅。这一章我们讲讲——Prompt Engineering，虽然现在已经叫harness甚至graph engineering了，但是其中的最基础的部分还是在怎么使用prompts。而且为这章设计的交付物还挺有用：一个简历优化器。

## 第 2 页 · 本章路线

先看地图，这一章分四块。第一块，prompt 的基本功：消息角色、few-shot，还有一套好的 system prompt 的公式。第二块，模型的旋钮：temperature 参数，token是怎么计算的。第三块，工程化的实现结构化输出：三步演进，让模型的话变成程序能直接消费的数据。最后一块，实战：把前面所有东西攒进一个简历优化器。

## 第 3 页 · 01 · 分隔页：Prompt Engineering 与消息角色

尽管现在各种agent也可以帮你写提示词，但是作为一个工程师还是需要有能判断提示词好坏的能力的，尤其是在后面调试应用的trace时，这个判断力很重要。chapter1的指令写给编程助手，这一章，同样的四要素写给**模型本身**。而且这不是重复造轮子——后面 Ch3 做 RAG，检索结果怎么拼进模板，都是 prompt；Ch4 做 Agent应用，系统指令和工具描述，还是 prompt。一句话：**prompt 写不好，上层架构再漂亮也没用。**

## 第 4 页 · 从「指令四要素」到 Prompt Engineering

看屏幕这张映射表。**任务**，变成 system prompt 里的角色与任务定义；**上下文**，是 user 消息里每次贴进去的材料；**约束**，是输出格式、语气、规则；**验收标准**，升级成两件武器——few-shot 示例，加 Pydantic 校验。

四要素一个没变，只是换了收信人。重点看最后一行：验收从「我肉眼看着对」，升级成「程序能验证对不对」。这两件武器就是本章的主角，待会儿挨个登场。

## 第 5 页 · messages 的三种角色

屏幕这段代码就是真实输入给LLM的数据，现在正式认识三个角色。**system** 是员工手册，定义它是谁、守什么规矩；**user** 是工单，每次的具体输入；**assistant** 是聊天记录，LLM的回复。

两个要点，第一，**模型本身没有记忆**。你看到的连续对话，是程序把历史消息每次完整重发一遍——所以对话越长，越慢，回复效果越差。这就是 上下文需要压缩管理 的底层原因。第二，**system 的优先级高于 user**。角色、规则、输出格式一律写进 system，别每次在 user 里重复。system尽量不要去做变化，会影响大kvcache，这个我们后面再聊。

## 第 6 页 · 好 system prompt 的四件套

公式在屏幕上：**角色＋任务＋规则边界＋输出格式**。四件各回答一个问题：你是谁、做什么、必须怎样绝不怎样、以什么形式返回。

缺了哪个都有具体后果：缺角色，回答像百科全书，正确但没用；缺规则，输出空洞没有明确指向；缺输出格式，后面没法结构化对接。

## 第 7 页 · few-shot：给例子胜过给描述

有时候标准特别难用语言描述——比如「把简历句子改得专业有力」。你写「要专业、有力、量化」，模型没有办法理解你要求的“专业”到底是什么标准，什么程度。

这时候别堆形容词，直接给一对例子。屏幕上就是：输入「负责公司内部系统的开发维护工作」，输出「独立负责 3 个内部系统的开发与迭代，工单处理时长从 2 天压缩至 4 小时」。注意，量化数字、动词开头、成果导向——这就是有控制的边界，LLM就能理解“专业”就是指这样的输出标准。

所以，例子一定要覆盖你想控制的边界，尽可能泛化。

## 第 8 页 · 02 · 分隔页：温度、参数与 token 账本

第二部分，看下LLM的几个输入参数。prompt 决定下限，参数决定性格。讲三样：temperature、max_tokens，还有一本和钱直接挂钩的 token 账本。这部分的实验精神就一句话：**调参之前，先亲眼看现象。**

## 第 9 页 · temperature：模型的性格旋钮

temperature 就是 LLM 的性格旋钮。先说一句原理：LLM 是一个词一个词往外蹦的，每蹦一个词之前，它手里都有一份「候选词概率排行榜」。temperature 调的就是这份榜单的**差距**——调低，第一名的优势被拉到无限大，回回都选它，输出稳定、可复现；调高，名次之间的差距被抹平，冷门词也有机会被选中，输出发散，有惊喜也有惊吓。

落到屏幕这张表。**0 到 0.3**，刻板、稳定、可复现，适合结构化输出、分类、改写——本章的简历优化器就用这档。**0.4 到 0.7**，平衡，适合周报、总结、通用问答。**0.8 到 1.0**，发散，留给头脑风暴和创意文案。

来，**弹幕猜一下**：让模型帮团队脑暴名字，用哪档？对，往 1.0 靠——这种任务就怕它太规矩。

另外两个参数知道存在就行：max_tokens 是输出长度上限，当保险丝用，防失控烧钱。top_p 是另一档随机性旋钮，管的是候选名单本身——不动概率差距，直接砍名单：top_p 等于 0.1，就是只从榜单前几名、累计概率 10% 的那一小撮里挑，后面的长尾冷门直接出局。它和 temperature 殊途同归，实战里改一个就够，一般只动 temperature。

最后给这一节降降温，说句实话：**这个参数没有听起来那么重要**。推理类模型——比如 DeepSeek 的 deepseek-reasoner——API 层面干脆不让调 temperature，设了也会被忽略。而且实际做应用要输出稳定，靠的是后面讲的 JSON mode 加校验，不是拧温度。那为什么还要花一页讲它？因为重点从来不是这个旋钮，是它背后的概念：**LLM 的输出是从概率分布里采样出来的**。理解了这一点，你才知道为什么同一个问题两次答案不一样、为什么程序必须做校验——这个认知，比记任何参数都值钱。

## 第 10 页 · token：模型眼里的文字

最后一个概念，token，纯科普。你看到的文字，模型看到的不是文字，是一串 token——**token 是模型读和写的最小单位**。换算给个直觉：一个汉字大概 1 到 2 个 token，一个英文单词大概 1 个，越生僻的词被切得越碎——unbelievable 这种长单词，可能被拆成三块。

懂了这个概念，很多现象就通了。经典的「strawberry 里有几个 r」模型老数错，就是因为它看到的是 token，不是一个个字母。前面说的上下文窗口，单位也是 token——所谓「上下文 128K」，就是模型一次能装下十三万 token 左右；max_tokens 限的同样是输出的 token 数。计费也一样，API 按 token 收钱。

## 第 11 页 · 03 · 分隔页：结构化输出

第三部分，工程化最重要的一节。第0章说过，JSON 是数据的世界语——但模型吐出来的是**文本**，你的程序要的是**数据**。把文本变成数据，就是工程化最重要的基石。

顺带再提一下——Function Calling，工具调用：把函数预先登记给模型，需要使用时用 JSON 报出函数名和参数，你的程序执行完，把结果喂回去。也是结构化输出的一部分，LLM和程序之间传的，必须是结构化数据。工具调用Ch4 那章会详细将；这一章先重点「让模型可靠输出数据」。接下来三步演进，可以跟着仓库里的 json_parsing_demo.py，一步步跑。

## 第 12 页 · 第 1→2 步：从「口头约定」到 JSON mode

第一反应人人都会：prompt 里写一句「只输出 JSON」，拿 json.loads 去解析。跑一次成了，然后下次很可能就翻车——LLM给 JSON 套个 markdown 代码块，或者贴心地在前面加一句「好的，以下是您要的 JSON」，解析当场报bug。它不是「答错了」，它只是**不可靠**。

所以第二步，把口头约定改成白纸黑字。顺带说一句，这不是 DeepSeek 的独家功能——OpenAI、Gemini、Qwen、Kimi、GLM 全都有对应参数，写法大同小异。看屏幕代码，就两个重点：第一，目标结构写进 **system** 消息，别写在 user 里；第二，加上 response_format 那一行开启 JSON mode，之后拿到的 content 就是纯 JSON，直接 loads，稳了。

## 第 13 页 · 第 3 步：Pydantic 校验（工程级）

但 JSON mode 只保证「是合法 JSON」，不保证**字段和类型**符合约定——某个value要的是数组，它可能返回一整个字符串。因为**合法 JSON 不等于字段正确**

第三步上 Pydantic：用类定义结构，model_validate 一验，类型不对当场精确报错——错在哪个字段、差在哪，非常清楚。过了校验，拿到的就是正经对象，有代码补全，像用普通类一样用。而且，Pydantic 本身就是python后端开发必用的库，也是FastAPI 的内置校验库，几乎是必须掌握的。

## 第 14 页 · 失败了怎么办：把报错喂回去

那校验失败了怎么办？有没有重试机制呢，有的，正确姿势是**把报错喂回模型**：把 ValidationError 原样作为新消息发回去——「你返回的 JSON 中 skills 应为数组，请修正后重新输出」——不过以目前大模型的能力很少发生。

这是生产环境处理模型输出的通用模式，叫自纠重试机制，我们工程化常用的机制。

## 第 15 页 · 04 · 分隔页：实战——简历优化器

第四部分，我们实战一个简单的作业。需求一句话：输入一段简历文本，输出结构化的改进建议。

为什么选这个？因为它够真实——也是使用频率比较高，手边必然有资料的一个场景。

## 第 16 页 · 结构先行：先设计输出，再写 prompt

一个好的习惯：**结构先行**——先想清楚要什么，再写 prompt。屏幕上就是五个字段的设计：overall_score，总分；strengths，保留的优点，最多三条；issues，问题清单，每条带维度、问题、建议；star_rewrites，改写示例，原句、改写、理由三件套；最后 keywords_to_add，建议补充的关键词。

## 第 17 页 · v2 标准写法与最终效果

v0、v1 在第 12 页都体验过了，不用再练一遍，直接看最终形态 v2 长什么样。标准写法就三块，看屏幕左边：第一块，**Pydantic 输出模型**——把上一页那五个字段落成类定义，这就是整个程序的「合同」；第二块，调模型走 JSON mode，拿到结果先 model_validate，失败就把报错喂回去重试——第 12 到 14 页的组合拳在这里合体；第三块，把校验过的对象打印成五板块报告——中间的 JSON 只是技术手段，使用者看到的最终产物是这份报告。

效果就是屏幕右边这样：总分、保留的优点、带维度和建议的问题清单、STAR 改写、补充关键词。验收口径不变：**「能跑」不算完成，跑 sample_resume.txt 出来长这样才算**，然后再跑你自己的。

vibe coding 时代，这些代码还要自己写吗？——不用，这套程序就该让 AI 写。但是**那五个字段的结构设计，就是你的需求书和验收标准**。你总得知道有哪些技术手段来规范LLM的输出吧。跑出来的东西过没过校验、bug原因，你也得看得懂。你的技术taste，**「要什么」和「长什么样算好」得告诉AI**。

## 第 18 页 · 实战演示：跑一次简历优化器（录屏）

光说不练假把式，看一段真实录屏。跑的就是仓库里那份典型差简历，命令就一行：python resume_optimizer.py sample_resume.txt。

重点看三个地方：第一，报告五板块齐不齐，每条建议是不是都落到简历原文上了；第二，末尾的 usage 字段，这次调用花了多少 token；第三，同样的命令换成你自己的简历，看看 AI 给你打多少分。**跑通的弹幕刷个 🎉，敢把自己总分发评论区的，我敬你是条汉子**——我猜没几个超过 70 的。

## 第 19 页 · 本章小结 + 预告（结尾 CTA）

简单收个尾。这一章主要三样东西：一套判断 prompt 好坏的基本功——四件套公式，加 few-shot；一个底层认知——LLM 的输出是从概率分布里采样出来的，所以工程上必须做校验；一套组合拳——JSON mode 拿到合法 JSON，Pydantic 卡字段，失败就把报错喂回去自纠。最后把这些知识融合进简历优化器，记得 push 上 GitHub。
