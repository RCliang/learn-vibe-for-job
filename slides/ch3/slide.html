01 · Embedding

Embedding：给文本一个语义坐标

我想请年假
年假申请流程
年假能结转吗
今晚吃什么
明天天气
近 远 语义空间（示意）

直觉

Embedding 模型把一段文本变成一串很长的数字（向量，如 1024 个数）——它就是这段文本的语义坐标：意思相近，坐标就靠近。「我想请年假」和「年假申请流程」字面不同，坐标却挨着。

余弦相似度

衡量两个向量「方向有多一致」：-1 到 1，越接近 1 越相似。数学不神秘，几行代码就能算——实验里亲手写一遍。

地基
意思近 = 坐标近——这一句就是语义检索的全部秘密。
01 · Embedding 实操

调用 Embedding API：换一把钥匙而已DeepSeek 只有对话 API —— 本章向量化改用硅基流动，bge-m3 免费（本章 0 元）

client = OpenAI(api_key=EMBED_API_KEY, base_url="https://api.siliconflow.cn/v1") # 换 base_url resp = client.embeddings.create( model="BAAI/bge-m3", # 免费中文向量模型 input=["我想请年假去旅游", "年假的申请流程是什么"], ) vectors = [d.embedding for d in resp.data] # 每句话一个 1024 维向量
🔑 从本章起 .env 里有两把钥匙

对话走 DeepSeek（LLM_API_KEY），向量化走硅基流动（EMBED_API_KEY）——各管一件事，别塞混。接口都是 OpenAI 兼容，代码几乎不变。

为什么是硅基流动

国内手机号注册（cloud.siliconflow.cn），注册送额度；bge-m3 中文向量模型免费。本章全部向量化花费 0 元。

实验：embedding_lab.py

六句话（两组同主题 + 两句无关），两两算余弦相似度、从高到低排序。

你会看到：同主题句对稳定排在无关句对前面——「意思近 = 坐标近」变成你自己的实验结论。

02 · 切分与入库

切分：chunk_size 与 overlap

为什么不整篇塞进去？① 超上下文窗口、还贵；② 检索粒度太粗——问「餐补」，捞出整篇报销制度。切成小块，按需取用。

chunk_size · 每块多大（中文常用 300–500 字）

太大 → 检索不精准：一块里混着多个主题
太小 → 上下文碎、语义不完整
面试问「chunk 怎么定」：给区间 + 「用评估验证」

overlap · 相邻块重叠多少（常用 50）

防止关键句正好被切在边界上，两边都检索不到。块与块是「叠着走」的。

# 块与块叠着走（overlap=50） |────── 块1 ──────| |────── 块2 ──────| |────── 块3 ──────| ←重叠→

先手写，再用框架

手写滑窗切分（split_text，十几行）——先懂本质；LangChain 的 splitter 是同样思想的工程化版本。

02 · 切分与入库

Chroma：能按语义查找的抽屉本地内嵌向量数据库 · pip install chromadb · 数据落在 ./chroma_db · 零运维

import chromadb client = chromadb.PersistentClient(path="./chroma_db") collection = client.get_or_create_collection("company_kb") # 存：id + 原文 + 向量（显式传 bge-m3 的结果） collection.add(ids=["leave_0"], documents=["年假 10 天..."], embeddings=[[0.1, ...]]) # 查：问题也向量化，拿回余弦距离最近的 k 块 result = collection.query(query_embeddings=[[0.2, ...]], n_results=3)
⚠️ 为什么显式传向量？

Chroma 默认会自动下载一个英文向量化模型——国内下载慢、中文效果差。显式传入 bge-m3 的结果，检索质量我们自己说了算。

三者分工（面试爱问）

向量库：只管存和查
Embedding 模型：语义在这里
LLM：只负责最后的生成
三个角色各司其职——换语义就换 embedding，换文风就换 LLM

03 · 检索增强生成

链路三步：检索 → 拼接 → 生成

① 检索retrieve(question, k=3)→ ② 拼接build_prompt · 编号入 prompt→ ③ 生成DeepSeek · 带引用回答

第 ② 步之后，模型看到的 prompt 长这样：

【参考资料】 [1] 年假当年有效，最多可结转 5 天到次年 3 月底…… [2] 请年假需提前 3 个工作日在 OA 系统提交…… 【问题】年假可以结转吗？

「增强」发生在第 ② 步

把检索到的资料编号拼进 prompt——就这一步，没有更多魔法。

资料怎么拼、纪律怎么写，全是 Ch2 的 prompt 功夫：结构、规则、few-shot 都用上了。

03 · 检索增强生成

幻觉抑制：三条 prompt 纪律写在 SYSTEM_PROMPT 里——拼了资料，模型仍可能夹带私货

1

只用资料

只根据【参考资料】回答，不许用自己的知识补充

2

标注引用

引用处标 [1] [2]——可回溯、可验证，用户能自己去原文核对

3

诚实拒答

资料不足就明确说「知识库中没有找到相关内容」，禁止编造

面试
问「怎么处理幻觉」——这三条就是标准答案之一。全部是 prompt 层约束：不改模型、不训练，这就是 Prompt Engineering 在工程里的分量。

04 · 效果评估

最小路径：LLM as judgechunk 300→600、top-k 3→5，效果好了还是差了？「感觉差不多」不算数

qa_pairs.json

10 条测试问答：问题 + 标准答案，从语料里出的题
测试集是地基——题目歪了，后面全歪

judge_eval.py

每条问题跑一遍 RAG → 让模型扮演评委，按 1–5 分打分
评委输出用 JSON mode 拿结构化分数——Ch2 的手艺直接复用；评委温度必须 0

eval_results.jsonl

每次评估追加一行（带 label）
天然支持多组对比：三行记录并排比 avg

评估的对象是「检索 + 生成」整条链路——所以它能告诉你该改哪头，而不只是「好/不好」。
04 · 效果评估

调优实验：把结论落成一句话

python build_kb.py --chunk 300 python judge_eval.py --label "chunk300" python build_kb.py --chunk 600 # 重建库 python judge_eval.py --label "chunk600" python judge_eval.py --k 5 --label "chunk300-k5" # 打开 eval_results.jsonl： # 三行记录，对比 avg，找到最弱的一题
⚠️ 常见坑

改了 chunk 必须重新 build_kb——旧库不重建，评的还是老切分。

有据回答，长这样

「在我的测试集上，chunk=300 平均 4.6 分、chunk=600 平均 4.1 分、k=5 与 k=3 持平，所以选 300 / 3。」

面试里聊调参，说得出这句话的人和说「我感觉差不多」的人，不在一个档次。

注意措辞的严谨：结论限定在「我的测试集上」——换语料要重跑，这是评估的基本素养。

04 · 效果评估 · 完整路径

Ragas 四指标：先定位维度，再动手改业界标准框架 · 每项 0–1 分，越高越好 · 选做：ragas_eval.py（评委走 DeepSeek、向量走硅基流动）

指标评什么低分说明什么（怎么改）
Faithfulness回答忠于检索资料（不编造）生成端在编造 → 检查三条纪律 / 降温度
AnswerRelevancy回答切题prompt 指令模糊 → 收紧任务定义
ContextPrecision检索结果里相关内容的占比检索不准 → 调 chunk / 换 embedding
ContextRecall标准答案被检索覆盖的程度检索不全 → 调大 top-k / 改切分
四个数字出来，先定位是哪个维度低，再决定改检索端还是生成端——别拿着锤子到处敲。
04 · 进阶视野

GraphRAG：向量 RAG 不是银弹

向量 RAG 的两个天然短板

① 多跳 / 枢纽问题
「部门总监负责审批哪些事项？」——答案一半在请假制度、一半在报销制度；靠「部门总监」这个实体把两份文档关联起来，而语义相似度不认识「关联」。

② 全局性问题
「这套制度的整体设计思路？」——答案散落在所有文档里，top-k 装不下全貌。

GraphRAG 的思路

用 LLM 从语料抽实体和关系（三元组，如「事假—审批人—部门总监」），构建知识图谱；检索时沿图的边多跳推理或按实体聚合。

代价：图构建要大量 LLM 调用，贵，更新需重算。
选做：graph_rag_mini.py（约 10 分钟）亲手建一张小图——前两题图更完整，第三题向量反而更直接

面试一句话
默认用向量 RAG；用评估证明它答不好多跳 / 全局问题了，才考虑 GraphRAG——没有银弹，只有合适。
